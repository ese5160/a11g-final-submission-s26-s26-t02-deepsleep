Project
Overview

The Device

The Smart Art Protection Frame attaches to artwork frames to continuously track environmental conditions, physical disturbances, and visual anomalies. When a security event is detected, it autonomously captures a photo and pushes an alert via cloud MQTT.

The Problem

Traditional artwork protection is either prohibitively expensive (museum-grade) or inadequate (simple motion alarms). This device fills the gap for small galleries, traveling exhibitions, and private collectors who need affordable, professional-grade remote monitoring.

Internet Augmentation

Sensor telemetry is continuously published to an Azure-hosted MQTT broker, where Node-RED flows visualize it on a dashboard. Alarm images are Base64-encoded and uploaded in chunks. Display content and firmware updates are both managed remotely over Wi-Fi.

System
Architecture

TASK 01
Network Task
Wi-Fi association, MQTT publish/subscribe, OTA firmware update coordination. Implements flag-based decoupling to prevent stack overflow during OTA.
TASK 02
Data Task
Sensor polling at defined intervals — SHT30 every 1 s, BNO085 IMU every 100 ms — and LCD refresh from cloud-configured artwork metadata every 2 s.
TASK 03
Security Task
Evaluates trigger conditions every 20 ms. Generates valid alarm event only after 200 ms continuous threshold breach. Highest priority task in the scheduler.
TASK 04
Camera Task
On alarm, initiates SPI capture command to OV2640, buffers the 320×240 JPEG, then publishes Base64-encoded chunks over MQTT with sequence numbers and CRC.

Sensors & Peripherals

SHT30
I2C0 · 0x44
Temperature & humidity. High-repeatability mode (0x2400), sampled every 1 s with CRC8 validation on the 6-byte response.
BNO085
I2C0 · 0x4A
6-axis IMU sampled every 100 ms. Normalized vector magnitude thresholded by the Security Task to detect movement or impact.
FSR
ADC · GPIO30
Measures frame mounting pressure. Baseline at boot; delta >220 ADC counts triggers alarm. Recovery <120 counts clears it.
OV2640
GSPI · I2C1
320×240 JPEG capture via SPI data burst and SCCB register programming on a dedicated I2C1 instance.

Key Technical
Challenges

Challenge 01
SCCB vs. I2C Protocol Mismatch

After porting the OV2640 driver to the SiWx917 SDK, camera initialization appeared to succeed but image capture produced corrupted or empty FIFO data. The root cause: standard I2C requires an ACK from every slave byte. The SDK's sl_i2c_driver_send_data_blocking() treats missing ACK as a fatal error. SCCB, however, officially marks the slave ACK as "don't care" — all register writes were flagged as failures, aborting initialization mid-table.

Fix: treat SL_I2C_NACK as equivalent to SL_I2C_SUCCESS in the SCCB wrapper. The camera is also isolated on a dedicated I2C1 instance to prevent NACK-tolerant behavior from interfering with other sensors.

static sl_i2c_status_t sccb_write(uint8_t reg, uint8_t val) {
    uint8_t buf[2] = { reg, val };
    sl_i2c_status_t st = sl_i2c_driver_send_data_blocking(
                             I2C_INSTANCE, OV2640_ADDR, buf, 2U);
    return (st == SL_I2C_NACK || st == SL_I2C_SUCCESS)
           ? SL_I2C_SUCCESS : st;
}
Challenge 02
OTA Stack Overflow

The Network Task originally ran Wi-Fi, MQTT, HTTP manifest fetch, and OTA download in a single loop. The nested call chain — MQTT handler → sl_http_client_send_request() → sl_wifi_start_stateless_otaf() — with its internal TLS buffers and deep callbacks exceeded the 6144-byte stack, triggering vApplicationStackOverflowHook.

Fix: the MQTT handler only sets a flag. The main loop executes OTA from a clean, shallow stack frame after the receive stack has fully unwound.

// MQTT handler — shallow context, just set flag:
if (topic matches OTA_NOW) { runtime_ota_requested = true; }

// Network Task main loop — clean stack, execute OTA:
if (runtime_ota_requested) {
    runtime_ota_requested = false;
    check_status = perform_manifest_version_check();
    if (check_status == SL_STATUS_OK && ota_available)
        run_ota_sequence();
}
Challenge 03
Automatic Software Reset After OTA

After OTA flash, the SiWx917 NWP requires a chip reset to boot the new image — initially requiring a manual hardware reset, unacceptable for a remotely managed device. Fix: the on-chip Window Watchdog Timer (WWDT) is armed after OTA completion and deliberately never fed. When the reset counter expires, MCU_WDT_BASED_CHIP_RESET cycles the SoC exactly as if the physical reset button were pressed.

static void net_init_watchdog_arm(void) {
    RSI_WWDT_Init(MCU_WDT);
    RSI_WWDT_IntrMask();
    MCU_AON->MCUAON_WDT_CHIP_RST_b.MCU_WDT_BASED_CHIP_RESET = 0U;
    RSI_WWDT_ConfigWindowTimer(MCU_WDT, NET_INIT_WDT_WINDOW_TIME);
    RSI_WWDT_ConfigIntrTimer(MCU_WDT, NET_INIT_WDT_INTR_TIME);
    RSI_WWDT_ConfigSysRstTimer(MCU_WDT, NET_INIT_WDT_RESET_TIME);
    RSI_WWDT_Start(MCU_WDT);
}
